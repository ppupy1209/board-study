이 문서는 기능 목록이 아니라 “어떤 문제를 보고, 무엇을 선택했고, 무엇을 포기했는가”를 남긴 기록입니다. [인프런 강의 커리큘럼](https://www.inflearn.com/course/%EC%8A%A4%ED%94%84%EB%A7%81%EB%B6%80%ED%8A%B8%EB%A1%9C-%EB%8C%80%EA%B7%9C%EB%AA%A8-%EC%8B%9C%EC%8A%A4%ED%85%9C%EC%84%A4%EA%B3%84-%EA%B2%8C%EC%8B%9C%ED%8C%90?cid=334365)의 MSA, 대용량 쿼리, 계층형 댓글, 동시성, Redis, Kafka, Transactional Outbox, CQRS, Request Collapsing 주제를 참고하되, UI·Docker 자동 적재·관측성·부하 테스트는 서비스화 과정에서 별도로 확장했습니다.

## 1. 학습용 게시판에서 모두의 광장으로

### 문제

백엔드 모듈과 테스트는 있었지만 저장소 이름과 설명이 학습 결과에 머물렀습니다. 처음 보는 사람이 사용 장면과 운영 방법을 떠올리기 어려웠고, API를 직접 호출하지 않으면 결과를 볼 수도 없었습니다.

### 결정

- 다양한 주제로 자유롭게 소통한다는 의미가 바로 드러나도록 제품 이름을 `모두의 광장`으로 정하고 자유게시판, 오늘의 인기 흐름, 시스템 상태를 한 화면에 배치했습니다.
- Docker Compose 한 번으로 UI, 9개 Spring 서비스, MySQL, Redis, Kafka, Prometheus, Grafana를 시작합니다.
- 기본 실행은 자유게시판의 100건 데모 데이터만 제공해 빠르게 시작합니다. 1,500만 건은 `large-data` 프로필로 최초 한 번만 로컬 MySQL 볼륨에 적재하고 이후 실행에서는 재사용합니다.

### 트레이드오프

모든 컨테이너를 로컬 한 대에서 띄우는 구성은 운영 배포 모델이 아닙니다. 대신 포트폴리오 검증 환경에서는 재현성과 관찰 가능성을 우선했습니다.

## 2. 1,500만 건 자유게시판 목록 조회 최적화

### 문제

`OFFSET 2,999,970`처럼 깊은 페이지는 앞선 행을 읽고 버립니다. Secondary Index를 이용하더라도 각 엔트리마다 본문 레코드를 다시 읽으면 random I/O가 페이지 깊이만큼 발생합니다.

### 비교한 선택지

1. 단순 `LIMIT ... OFFSET ...`: 임의 페이지 이동은 쉽지만 깊은 페이지 비용이 큽니다.
2. Keyset Pagination: 마지막 ID 이후만 읽어 일정한 성능을 얻지만 임의 페이지 번호 이동이 어렵습니다.
3. Covering Index + ID 선조회: OFFSET 스캔은 남지만 버리는 구간에서 본문 접근을 없앨 수 있습니다.

### 결정

페이지 번호 API에는 `(board_id, article_id)` Covering Index로 ID만 먼저 조회하고, 페이지에 필요한 30개 ID만 본문과 JOIN했습니다. 연속 탐색 UI에는 `article_id < lastArticleId` Keyset 방식을 별도 제공했습니다.

```sql
SELECT a.*
FROM (
  SELECT article_id
  FROM article
  WHERE board_id = :boardId
  ORDER BY article_id DESC
  LIMIT :limit OFFSET :offset
) page
JOIN article a ON a.article_id = page.article_id;
```

### 결과와 한계

기존 1,400만 건 실험에서 깊은 페이지 응답은 약 `3.8s → 0.3s`로 줄었습니다. 현재 재현 환경은 자유게시판 한 곳에 1,500만 건과 데모 100건을 넣어 같은 병목을 다시 측정할 수 있게 확장했습니다. 본문 random I/O는 30건으로 제한했지만 OFFSET 인덱스 스캔은 남습니다. 따라서 탐색 방식이 허용한다면 Keyset Pagination이 더 장기적인 해법입니다.

## 3. 계층형 댓글: 인접 리스트에서 Path Enumeration으로

### 문제

부모 ID만 저장하는 인접 리스트는 쓰기가 단순하지만, 무한 depth 목록을 정렬하거나 서브트리를 찾을 때 재귀 조회가 필요합니다.

### 결정

5자리 base62 chunk를 depth마다 이어 붙인 경로를 저장했습니다. 경로의 사전식 정렬이 화면의 댓글 순서가 되며, prefix 범위로 하위 댓글을 찾을 수 있습니다.

### 한계

한 depth의 자식 수와 전체 depth를 제한해야 합니다. 현재는 chunk 5자리, 최대 depth 5라는 제품 정책을 코드에 명시했습니다. 무제한이라는 표현보다 시스템이 보장하는 한도를 분명히 하는 편을 택했습니다.

## 4. 좋아요 수 동시성: 정합성과 처리량 사이

### 문제

좋아요 이력 저장과 집계 수 증가는 동시에 요청될 때 Lost Update가 발생할 수 있습니다. 매 요청을 무거운 전역 락으로 막으면 정합성은 얻지만 처리량이 떨어집니다.

### 결정

- `(article_id, user_id)` Unique Index로 중복 좋아요를 데이터베이스에서도 차단했습니다.
- 비관적 락, 낙관적 락, 단일 UPDATE 방식을 각각 구현해 충돌 빈도에 따른 선택 기준을 비교했습니다.
- 단순 카운터 증감은 `UPDATE ... SET like_count = like_count + 1` 원자 연산을 우선합니다.

### 배운 점

락 방식은 이름으로 고르는 것이 아니라 충돌 빈도, 재시도 비용, 임계 구역 크기로 결정해야 합니다. 읽고 계산한 뒤 쓰는 코드보다 DB가 한 문장으로 보장할 수 있는 연산이 더 단순했습니다.

## 5. 조회수: Redis 선반영과 어뷰징 방지

### 문제

읽기마다 DB 카운터를 갱신하면 인기 게시글 한 행에 쓰기가 집중됩니다. 같은 사용자의 반복 새로고침도 실제 관심보다 조회수를 부풀립니다.

### 결정

- `articleId:userId` 키를 TTL과 함께 선점해 짧은 시간의 중복 증가를 차단했습니다.
- 조회수는 Redis에서 먼저 증가시키고 일정 배수마다 DB에 백업했습니다.
- Redis 유실 시 마지막 백업 이후 값이 사라질 수 있음을 수용하고, 조회수의 비즈니스 중요도를 금전 데이터보다 낮게 분류했습니다.

## 6. 인기글: 이벤트 스트림과 Redis Sorted Set

### 문제

좋아요, 댓글, 조회 이벤트가 서로 다른 서비스에서 발생합니다. 인기글 서비스가 각 원본 DB를 계속 조회하면 결합도와 읽기 부하가 커집니다.

### 결정

Kafka로 변경 이벤트를 모으고 인기글 서비스가 가중 점수를 계산해 Redis Sorted Set에 저장합니다. 당일 생성 게시글만 집계해 오늘의 Top 10을 `ZREVRANGE`로 조회하고, 순위와 화면 표시용 조회 모델은 다음 날 01시에 만료합니다.

### 트레이드오프

인기글은 즉시 일관성이 아닌 최종 일관성을 택했습니다. 소비 지연이 생겨도 원본 좋아요·댓글 데이터는 유지되며, Consumer 재처리로 복구할 수 있습니다.

### 부하 테스트에서 발견한 호출 증폭

Redis Sorted Set에 Top 10 ID만 저장한 상태에서는 목록 요청 한 번이 Article Service 단건 조회 10회로 증폭됐습니다. 1 vCPU 조건에서 외부 요청이 100 req/s에 도달하자 p95가 1.83초까지 증가했습니다. 게시글 이벤트로 인기글 표시용 조회 모델을 함께 갱신하고 Redis `MGET`으로 읽도록 변경해, 동일 조건의 p95를 1.75ms로 줄이고 내부 단건 조회를 제거했습니다.

테스트 조건·Grafana 지표·실패 경로는 [인기글 조회 호출 증폭과 CQRS 읽기 모델](hot-article-load-test.md)에 별도로 기록했습니다.

## 7. DB 커밋과 Kafka 발행 사이: Transactional Outbox

### 문제

DB 저장 후 Kafka 발행에 실패하면 다른 서비스는 변경을 모릅니다. 반대로 Kafka를 먼저 발행하면 DB 롤백 시 존재하지 않는 변경이 전파됩니다.

### 결정

비즈니스 데이터와 Outbox를 같은 트랜잭션에 저장합니다. 커밋 직후 비동기로 즉시 발행하고, 실패해 남은 행은 스케줄러가 다시 발행합니다. 성공한 Outbox만 삭제해 at-least-once를 보장합니다.

### 반드시 따라오는 조건

at-least-once는 중복을 허용합니다. 따라서 Consumer는 이벤트 ID나 최종 상태 덮어쓰기로 멱등성을 가져야 합니다. Outbox만 도입하고 소비 측 중복을 고려하지 않으면 문제를 옮긴 것에 불과합니다.

## 8. 읽기 최적화: CQRS와 Request Collapsing

### 문제

게시글 한 화면은 본문, 댓글 수, 좋아요 수, 조회수를 함께 필요로 합니다. 요청마다 여러 서비스를 동기 호출하면 지연과 장애 전파가 커지고, 인기 게시글 캐시가 만료되는 순간 동일 원본 조회가 몰릴 수 있습니다.

### 결정

- 변경 이벤트로 읽기 전용 Query Model을 갱신했습니다.
- 목록 ID는 Redis Sorted Set에 유지하고 본문 조회 모델과 조합합니다.
- 동일 키 캐시 미스가 동시에 발생하면 한 요청만 원본을 조회하고 나머지는 그 결과를 기다리는 Request Collapsing을 적용했습니다.
- TTL에 작은 무작위 편차를 주어 여러 키가 같은 순간 만료되는 상황을 완화했습니다.

### 한계

읽기 모델 재구축 절차와 이벤트 순서 역전 대응이 운영 과제로 남습니다. 향후 이벤트 버전과 재처리 체크포인트를 명시할 계획입니다.

## 9. 존재하지 않는 게시글의 캐시 관통 방지

### 문제

조회 모델과 원본 DB에 모두 없는 게시글 ID는 캐시에 값이 남지 않아 반복 요청마다 Article Service와 MySQL을 다시 조회했습니다.

### 결정

- 원본이 404로 확인된 ID에 `MISSING` 값을 60~70초간 저장했습니다.
- 원본 장애를 부재로 잘못 캐시하지 않도록 404와 통신 오류를 분리했습니다.
- 게시글이 있을 때만 댓글·좋아요 수를 조회하도록 원본 호출 순서를 바꿨습니다.
- 2,000 req/s 콜드 미스에서 최초 원본 조회 200건이 동시에 발생해, Redis 잠금으로 한 요청만 원본을 확인하고 나머지는 결과를 기다리도록 보완했습니다.
- 잠금은 캐시가 비어 있을 때만 3초간 유지하고 요청별 토큰이 일치할 때만 해제합니다.

### 결과

2,000 req/s로 30초간 같은 존재하지 않는 ID를 요청했을 때 원본 조회가 `55,688건 → 1건`, p95가 `859.05ms → 1.26ms`로 줄었습니다. 변경 전에는 목표 시각에 시작하지 못한 요청이 4,313건 발생했지만 적용 후에는 60,001건을 모두 처리했습니다. 자세한 단계형 부하와 콜드 미스 검증은 [캐시 관통 방지 기록](cache-penetration.md)에 정리했습니다.

## 10. 관측성과 부하 테스트를 기능으로 취급하기

### 결정

- 모든 서비스가 `/actuator/prometheus`를 노출합니다.
- Prometheus가 HTTP 요청률, 지연, JVM 메모리와 MySQL 테이블 규모를 수집합니다.
- Grafana 대시보드는 서비스 UP, 전체 RPS, p95, JVM Heap, 추정 게시글 수를 한 화면에 배치합니다.
- k6는 일반 첫 페이지 트래픽과 깊은 페이지 도착률을 분리해 임계값을 검증합니다.

### 임계값

- 실패율 `< 1%`
- 일반 목록 p95 `< 500ms`
- 깊은 페이지 p95 `< 1,000ms`

수치는 합격을 보장하는 장식이 아니라, 로컬 환경에서 회귀를 발견하기 위한 출발점입니다. 실제 결과는 CPU, 메모리, 디스크와 적재 완료 여부를 함께 기록해야 비교할 수 있습니다.

## 11. 로그아웃 뒤에도 살아남는 Refresh Token 재사용 차단

### 문제

Access Token을 5분으로 줄이면서 Refresh Token을 도입했지만, 브라우저 쿠키만 지우는 로그아웃으로는 공격자가 미리 복사한 Token을 없앨 수 없었습니다. 같은 Token이 동시에 두 번 갱신되면 정상 재시도와 탈취 요청을 구분할 수도 없었습니다.

### 선택과 해결

- 고정 Refresh Token과 모든 요청의 세션 조회 대신 Refresh Token Rotation과 Token Family를 선택했습니다.
- Token 원문은 `HttpOnly` 쿠키로만 전달하고 DB에는 SHA-256 해시와 `ACTIVE → ROTATED → REVOKED` 상태만 저장했습니다.
- 같은 Token의 갱신은 비관적 행 잠금으로 한 건만 성공시켰습니다.
- 회전된 이전 Token이 다시 나타나면 신규 Token을 포함한 패밀리 전체를 폐기했습니다.
- 보안 상태 변경이 401 예외와 함께 롤백되지 않도록 재사용 탐지 트랜잭션의 커밋 경계를 분리했습니다.
- 재사용 탐지 Counter와 Prometheus 경보를 추가했습니다.

### 검증과 한계

Testcontainers MySQL 동시성 테스트 3건과 k6 실제 HTTP 재현을 통과했습니다. Guest 조회·글쓰기 흐름은 그대로 유지하면서, 로그인 사용자의 새 글만 Access Token의 회원 ID와 닉네임에 연결했습니다. 기존 게시글은 별도 갱신 없이 `modu_{writerId}` 표시를 유지합니다. 재사용을 감지해도 이미 발급된 Access Token은 최대 5분간 유효하며, 즉시 차단을 위해 모든 서비스가 세션 상태에 의존하는 비용은 이번에는 수용하지 않았습니다. 선택지, 상태 전이, 지표와 공격 재현은 [Refresh Token 재사용 차단 기록](refresh-token-replay.md)에 정리했습니다.
